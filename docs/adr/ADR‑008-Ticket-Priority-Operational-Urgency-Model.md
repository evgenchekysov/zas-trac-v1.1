ADR‑008: Ticket Priority & Operational Urgency Model

Статус: Proposed
Дата: 2026‑07‑13

Статус: Accepted
Дата: 2026‑07‑22

Контекст: ZAS‑TRAC Backend

-------------------------------------------------
Контекст
-------------------------------------------------

В системе ZAS‑TRAC жизненный цикл заявки определяется
состоянием Ticket.status (ADR‑003).

Статус отвечает на вопрос:

«На каком этапе обработки находится заявка?»

Однако статус не отражает важность заявки
и срочность реагирования.

В процессе развития диспетчерской подсистемы,
SLA‑контроля и будущей аналитики выявлена необходимость
введения независимой модели приоритетов.

Приоритет необходим для:

— диспетчеризации;
— сортировки заявок;
— SLA‑политик;
— эскалаций;
— уведомлений;
— аналитики;
— отчётности.

-------------------------------------------------
Решение
-------------------------------------------------

Каждая заявка имеет один и только один приоритет.

В системе вводится отдельная сущность:

Ticket.priority

Допустимые значения:

EMERGENCY
NORMAL
PLANNED

Дополнительно вводится состояние приоритета:

OPEN
LOCKED

Каждый тикет имеет один Priority
и одно состояние Priority.

-------------------------------------------------
Семантика приоритетов
-------------------------------------------------

EMERGENCY

Аварийная заявка.

Характерные признаки:

— отказ оборудования;
— риск простоя производства;
— риск безопасности;
— необходимость немедленного реагирования.

Отображение в UI:

🚨 Авария

---

NORMAL

Текущая заявка.

Характерные признаки:

— обычные эксплуатационные работы;
— неисправности без критических последствий;
— работы в рамках регулярной деятельности.

Отображение в UI:

🔧 Текущая

---

PLANNED

Плановая заявка.

Характерные признаки:

— профилактические работы;
— улучшения;
— регламентные мероприятия;
— работы без срочности выполнения.

Отображение в UI:

📅 Плановая

-------------------------------------------------
Создание заявки
-------------------------------------------------

При создании заявки пользователь может выбрать приоритет.

Допустим выбор:

EMERGENCY
NORMAL
PLANNED

Если приоритет явно не указан:

priority = NORMAL

назначается автоматически.

Поле Priority отображается пользователю
как выпадающий список.

Значение NORMAL является значением по умолчанию.

После создания заявки выбор пользователя
фиксируется как первоначальная оценка ситуации.

Состояние Priority после создания:

OPEN

-------------------------------------------------
Пересмотр приоритета
-------------------------------------------------

Первоначальная оценка Priority может быть пересмотрена
в процессе обработки заявки.

Исполнитель, участвующий в работах по заявке,
может инициировать запрос на пересмотр Priority.

Причинами пересмотра могут быть:

— фактическое выявление аварийной ситуации;
— уточнение состояния оборудования;
— изменение оценки рисков;
— выявление обстоятельств,
неизвестных при создании заявки.

Запрос исполнителя не изменяет Priority автоматически.

Каждый запрос на пересмотр должен фиксироваться
в audit‑журнале как отдельное событие.

Исполнитель сообщает информацию.

Окончательное решение принимает диспетчер.

-------------------------------------------------
Изменение приоритета
-------------------------------------------------

Изменять Priority имеют право:

✅ Dispatcher
✅ Admin
✅ SuperAdmin

Не имеют права:

❌ Worker
❌ Participant
❌ Creator заявки

Изменение Priority считается
административным действием.

Каждое изменение должно фиксироваться
в audit‑журнале.

Priority может изменяться только
в состоянии OPEN.

-------------------------------------------------
Фиксация приоритета
-------------------------------------------------

Priority может находиться
в одном из состояний:

OPEN
LOCKED

OPEN

Приоритет может пересматриваться
и изменяться уполномоченными пользователями.

LOCKED

Приоритет считается окончательно подтверждённым.

Изменение состояния:

OPEN → LOCKED

выполняется только явным действием:

✅ Dispatcher
✅ Admin
✅ SuperAdmin

После перехода в состояние LOCKED:

— изменение Priority запрещено;
— повторное открытие Priority запрещено;
— изменение Priority недоступно для всех пользователей системы.

Включая:

❌ Dispatcher
❌ Admin
❌ SuperAdmin

Фиксация Priority должна фиксироваться
в audit‑журнале отдельным событием.

-------------------------------------------------
Связь со статусом тикета
-------------------------------------------------

Priority и Status являются независимыми сущностями.

Status отвечает на вопрос:

«На каком этапе находится заявка?»

Priority отвечает на вопрос:

«Насколько важна заявка?»

-------------------------------------------------
Допустимые сочетания
-------------------------------------------------

EMERGENCY + NEW
EMERGENCY + ASSIGNED
EMERGENCY + IN_PROGRESS
EMERGENCY + PAUSED
EMERGENCY + DONE
EMERGENCY + CLOSED

NORMAL + любое состояние

PLANNED + любое состояние

Все комбинации допустимы.

-------------------------------------------------
Инварианты
-------------------------------------------------

Каждый тикет имеет ровно один Priority.

Каждый тикет имеет ровно один Status.

Каждый тикет имеет одно состояние Priority:

OPEN
или
LOCKED.

Priority не влияет на допустимые переходы статуса.

Status не изменяет Priority автоматически.

Priority не влияет на workflow.

Workflow не изменяет Priority автоматически.

Work Session не изменяет Priority автоматически.

LOCKED Priority не может быть изменён.

LOCKED Priority не может быть разблокирован.

Изменение Priority возможно только
при состоянии OPEN.

Приоритет может изменяться только
явным действием уполномоченного пользователя.

-------------------------------------------------
Использование в системе
-------------------------------------------------

Priority используется для:

— диспетчерской панели;
— сортировки заявок;
— SLA‑политик;
— уведомлений;
— эскалаций;
— аналитики;
— отчётности.

Состояние Priority используется для:

— фиксации окончательной оценки заявки;
— защиты аналитических данных;
— исключения изменения истории задним числом.

-------------------------------------------------
Audit Events
-------------------------------------------------

Для Priority используются события:

ticket_priority_changed

priority_review_requested

ticket_priority_locked

Все события должны фиксироваться
в соответствии с ADR‑004.

-------------------------------------------------
Связь с другими ADR
-------------------------------------------------

ADR‑003 — Ticket Lifecycle

Priority не изменяет жизненный цикл
и используется совместно со статусом.

ADR‑004 — Events & Audit

Изменение Priority,
запрос пересмотра Priority
и фиксация Priority
должны фиксироваться событиями.

ADR‑006 — Work Sessions & Time Tracking

Work Session не влияет на Priority автоматически.

Исполнитель может инициировать пересмотр Priority
на основании фактической ситуации,
выявленной в ходе выполнения работ.

ADR‑007 — SLA, Metrics & Reporting

SLA‑политики могут использовать Priority
для расчёта нормативов и порогов.

Для отчётности используется
зафиксированный (LOCKED) Priority.

-------------------------------------------------
Осознанно исключено
-------------------------------------------------

— автоматическое изменение Priority;
— вычисление Priority по Status;
— влияние Priority на workflow;
— дополнительные уровни Priority;
— автоматическая блокировка Priority;
— автоматическая разблокировка Priority;
— изменение LOCKED Priority;
— изменение Priority по факту создания Session;
— изменение Priority по факту перехода статуса.

-------------------------------------------------
Итог
-------------------------------------------------

Модель Ticket разделяется
на две независимые оси.

Status:

NEW
ASSIGNED
IN_PROGRESS
PAUSED
DONE
CLOSED

Priority:

EMERGENCY
NORMAL
PLANNED

Status определяет стадию процесса.

Priority определяет важность заявки.

Создатель заявки выполняет первоначальную оценку.

Исполнитель может инициировать пересмотр оценки.

Dispatcher принимает окончательное решение.

Dispatcher может зафиксировать принятое решение.

После фиксации Priority становится LOCKED
и не может быть изменён.

Совместное использование Status и Priority
является основой диспетчеризации,
SLA‑контроля,
аналитики
и отчётности системы ZAS‑TRAC.
