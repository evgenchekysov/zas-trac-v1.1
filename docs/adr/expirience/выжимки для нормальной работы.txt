Контекст ZAS‑TRAC
У нас зафиксирована архитектура backend и бизнес‑правила.
Все изменения ниже являются частью согласованной архитектуры.

Источник истины:
backend/services/ticket_service.py
backend/services/session_service.py
backend/README.md

Архитектурные решения Дня 29 считаются финальными и не пересматриваются
без отдельного архитектурного решения.

---

Инварианты ZAS‑TRAC (не обсуждаются повторно)

• Идентификация пользователей — только через Supabase auth.uid
• Backend не реализует JWT и RBAC
• Контроль доступа — Supabase RLS
• Сессии строго персональные
• Один пользователь — не более одной активной сессии
• Статус заявки — агрегированное состояние сессий
• PAUSED = нет активных сессий
• DONE = работы завершены в целом
• DONE может нажать любой participant
• DONE не переписывает прошлые сессии
• CLOSED — финальный статус (owner / admin)

Приоритет заявок (ВАЖНО)

• Каждая заявка имеет приоритет
• Приоритет — атрибут заявки, НЕ статус
• Приоритет не влияет на state‑machine статусов

Фиксированные уровни приоритета:
• EMERGENCY — аварийный
• HIGH — плановый высокий
• NORMAL — обычный (по умолчанию)
• LONG_TERM — долгосрочный / факультативный

Правила использования:
• Приоритет задаётся при создании заявки
• Изменение приоритета фиксируется в audit‑log
• Worker не может повышать приоритет выше NORMAL
• Admin / dispatcher может устанавливать любой приоритет

Приоритет используется для:
• сортировки очереди заявок
• уведомлений
• диспетчеризации
• будущих SLA и отчётов
