ZAS‑TRAC — Roadmap Beta / WTS
(траектория развития системы)
Назначение roadmap’а
Данный roadmap фиксирует направление и логику развития ZAS‑TRAC на этапе Beta / WTS.
====================================
Версия 1
====================================

Roadmap:

не является детальным планом задач;
не фиксирует конкретные сроки;
служит ориентиром решений и приоритетов.

Любые задачи, не укладывающиеся в roadmap WTS,
рассматриваются как выход за рамки текущей фазы.

🧭 Общая логика Beta / WTS

Beta‑версия ZAS‑TRAC должна показать,
что система понятна, управляема и жизнеспособна
в реальной эксплуатации.

Основной вектор:

от демонстрации → к реальным действиям;
от UI‑эффектов → к устойчивой логике;
от одиночного сценария → к многопользовательской работе.


🚀 ФАЗА 1. Операционное ядро (Core WTS)
Цель фазы:
Система выполняет базовую функцию управления заявками без сбоев и двусмысленности.
Что должно работать стабильно:

создание заявки;
взятие заявки в работу;
изменение статусов;
рабочие сессии;
единое состояние для всех пользователей.

Ключевая мысль:

Лучше меньше функций, но полностью честных.

❌ Не добавляются:

украшения UI;
автоматические сценарии;
сложные правила.


🚀 ФАЗА 2. Событийная прозрачность (Events & Timeline)
Цель фазы:
Сделать систему наблюдаемой.
Появляется понимание:

что произошло;
когда;
кем;
в каком порядке.

Реализуется:

событийная модель (audit / events);
таймлайн заявок;
корреляция действий и изменения состояний.

Ключевая мысль:

Если нельзя восстановить историю — системе нельзя доверять.


🚀 ФАЗА 3. Многопользовательская реальность
Цель фазы:
Убедиться, что системой можно пользоваться одновременно.
Фокус не на нагрузки, а на поведение:

несколько людей видят одно состояние;
изменения не конфликтуют;
система не «расползается».

Важно:

Пусть медленно, но одинаково честно для всех.


🚀 ФАЗА 4. Операционные уведомления (Telegram)
Цель фазы:
Вынести ключевые события за пределы интерфейса.
Реализуется:

однонаправленные уведомления;
рабочий Telegram‑чат;
минимальный, но полезный набор сообщений.

Ключевая мысль:

Система существует не только в браузере.

❌ Telegram не рассматривается как интерфейс управления.

🚀 ФАЗА 5. Проверка на реальную полезность
Цель фазы:
Получить честный ответ на вопрос:

«С этой системой удобно работать людям?»

Проверяется:

понятность интерфейса;
логика действий;
отсутствие скрытых состояний;
отсутствие ручных обходов процесса.

Результатом фазы являются:

замечания;
точки трения;
подтверждение или корректировка логики.


🚫 Что сознательно НЕ делается в Beta / WTS
Зафиксировано как последующие этапы:

отчёты и аналитика;
оптимизация производительности;
сложные роли и права;
тонкая автоматизация;
интеграции с внешними системами.

Добавление этих вещей в WTS считается
нарушением фокуса этапа.

🧠 Принцип принятия решений в Beta
При любых сомнениях используется правило:

Что поможет пользователю
быстрее и понятнее выполнить работу сегодня
— то и приоритетно.

Если решение:

усложняет понимание;
скрывает логику;
требует пояснений —

оно противоречит целям WTS.

✅ Статус roadmap’а
Этот roadmap:

фиксирует траекторию развития;
используется как фильтр идей;
действует до завершения Beta / WTS.

Изменение roadmap’а возможно
только отдельной зафиксированной записью.

ЗАВЕРШЁННЫЙ ЭТАП (ДЕНЬ 8)
WTS: End-to-End базовый контур системы

Система переведена из состояния “архитектура готова”
в состояние “есть рабочий пользовательский контур”.

Реализовано:

Frontend:
- единый routing (App.jsx)
- устранён конфликт Router.jsx
- реализован Landing (публичная точка входа)
- реализована форма создания заявки (/create)
- Dispatcher переведён на Layout (Sidebar + Header)
- UI подключён к backend без CORS (single origin)

Backend:
- переход на service_key
- устранены RLS ограничения
- API /tickets стабильно работает
- реализован публичный POST /tickets
- введён dev-mode bypass для auth

UX поток:
- пользователь может создать заявку без авторизации
- авторизованный пользователь может работать в Dispatcher
- UI выполняет реальные действия (не read-only)

Ключевой результат:
Система работает end-to-end:
создание → отображение → управление заявками

Ограничения:
- auth работает в dev-режиме (JWT отключён)
- оборудование не связано с assets (ввод вручную)
- нет отображения asset / location в Dispatcher

Ключевой переход:
из модели “части системы работают отдельно”
в модель “единый управляемый контур”
