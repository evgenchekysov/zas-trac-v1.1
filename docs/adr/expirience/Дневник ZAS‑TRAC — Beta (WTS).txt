ZAS‑TRAC — Beta / Working Test System (WTS)

================================================================

Назначение дневника
-------------------
Данный дневник предназначен для фиксации работ по сборке
рабочей тестовой системы ZAS‑TRAC (Working Test System).

Назначение WTS‑дневника:
— документирование фактических шагов реализации;
— фиксация принятых решений и компромиссов;
— осознанная фиксация технического долга;
— опора для перехода к опытной и промышленной эксплуатации.

Данный дневник является ОСНОВНЫМ ИСТОЧНИКОМ ИСТИНЫ
для этапа Beta / WTS.
Все новые решения и изменения в системе опираются на него
и на документ
«ZAS‑TRAC — Операционная логика v1.1».

================================================================

ЦЕЛЬ WTS (ЗАФИКСИРОВАНО)
-----------------------
К концу фазы Working Test System должно быть возможно:

✅ завести заявку;
✅ назначить / взять заявку в работу;
✅ вести работу по заявке (рабочие сессии);
✅ видеть актуальные статусы заявок;
✅ видеть историю / таймлайн событий;
✅ работать нескольким людям одновременно;
✅ получать уведомления в Telegram‑боте.

Не требуется (ОСОЗНАННО ИСКЛЮЧЕНО):

❌ идеальный UI;
❌ полная автоматизация процессов;
❌ отчёты и аналитика;
❌ сложная ролевая модель.

### 1. Среда разработки

Вся разработка ZAS‑TRAC на этапе WTS ведётся
ИСКЛЮЧИТЕЛЬНО В WEB‑СРЕДЕ.

✅ Используем:
— GitHub (web);
— GitHub Codespaces;
— Supabase (web‑console);
— Railway (web‑console);
— браузер (UI, API, диагностика).

❌ Не используем:
— локальные IDE;
— локальные базы данных;
— локальные dev‑серверы;
— машинозависимые окружения.

Причины:
— воспроизводимость среды;
— отсутствие ситуации «работает только у меня»;
— готовность к совместной работе;
— соответствие реальной эксплуатации.

----------------------------------------------------------------


### 2. UI и frontend‑контур

UI на этапе Beta / WTS рассматривается как тонкий клиент (thin client),
НО с обязательным требованием юзер‑френдли структуры.

Требования к UI WTS:

✅ UI должен быть КЛИКАБЕЛЬНЫМ:
— все ключевые действия выполняются через интерфейс;
— без консоли, без ручных запросов, без внешних инструментов.

✅ UI должен быть ПРОСТЫМ ДЛЯ ПОНИМАНИЯ:
— пользователь понимает, что происходит, без объяснений;
— действия имеют очевидные последствия;
— статусы, приоритеты и состояние заявок читаются визуально.

✅ UI должен демонстрировать:
— логику системы;
— жизненный цикл заявки;
— роли участников;
— актуальное состояние работ.

UI на этапе WTS МОЖЕТ:
— быть визуально грубым;
— не иметь финального дизайна;
— использовать простую верстку;
— не соответствовать бренд‑гайдам.

UI на этапе WTS НЕ МОЖЕТ:
— быть «красивой заглушкой» без реальной интерактивности;
— требовать устных пояснений для понимания;
— скрывать состояние системы;
— маскировать логику за декоративными элементами.

Принцип WTS‑UI:
"Лучше понятно и грубо, чем красиво и непонятно".

UI не является источником истины.
Его задача — честно и наглядно отображать
состояние системы и логику процессов.

----------------------------------------------------------------

### 3. Архитектура и источник истины

Источник истины системы — backend и база данных,
а НЕ пользовательский интерфейс.

Цепочка ответственности:

UI
 ↓
Backend API (бизнес‑правила)
 ↓
Supabase (Auth + DB + RLS)
 ↓
Events / Audit
 ↓
Telegram‑уведомления

✅ Backend:
— реализует бизнес‑логику;
— управляет статусами заявок;
— управляет рабочими сессиями;
— формирует события.

✅ Supabase:
— единственный источник идентификации (auth.uid);
— контроль доступа реализован через RLS;
— backend не может обойти ограничения базы.

✅ UI:
— не хранит долгоживущее бизнес‑состояние;
— client‑side состояние допускается только
  как временное WTS‑решение.

----------------------------------------------------------------

### 4. Допустимый технический долг (WTS)

Технический долг НА ЭТАПЕ WTS допускается, если:

✅ он не нарушает операционную логику v1.1;
✅ он явно зафиксирован в дневнике;
✅ понятен путь его устранения.

Примеры допустимого WTS‑долга:
— localStorage как временный источник данных;
— статический seed‑набор;
— упрощённая маршрутизация;
— отсутствие обработки редких edge‑cases.

НЕдопустимо:
— технические решения, противоречащие логике v1.1;
— «временные костыли» без фиксации;
— неявное состояние системы.

----------------------------------------------------------------

### 5. Telegram‑бот

Telegram‑бот в WTS используется ТОЛЬКО
как канал уведомлений (one‑way).

✅ Бот:
— получает события от backend;
— отправляет уведомления в рабочий Telegram‑чат.

❌ Бот не:
— принимает команды;
— управляет системой;
— изменяет данные;
— подтверждает действия.

Минимальный набор уведомлений фиксируется отдельно
и является частью WTS‑контракта.

----------------------------------------------------------------

✅ На этапе WTS:

❌ Railway не является средой разработки.
Backend проектируется как платформонезависимый.

Выполнена корректная интеграция Supabase Auth:

Используется JWT access_token, полученный после аутентификации пользователя.
Magic‑link OTP осознанно не используется как источник идентичности.


Реализован dependency get_current_user_id:

извлекает Authorization: Bearer <access_token>;
валидирует токен через Supabase SDK;
возвращает auth.uid как канонический user_id.


Диагностический эндпоинт:

GET /diag/whoami возвращает корректный user_id при валидном токене;
при отсутствии или невалидном токене возвращается 401 Unauthorized.



Swagger / UI

В Swagger подключена схема безопасности HTTPBearer.
Кнопка Authorize доступна и используется штатно.
Ошибка двойного Bearer выявлена и устранена.
Подтверждено, что Swagger корректно прокидывает заголовок Authorization.


🧠 Принятые решения

Supabase является единственным источником аутентификации.
Backend принимает только access_token, полученный в результате аутентификации.
User ID в системе = auth.uid (Supabase).
Magic‑link используется только как механизм входа, но не как токен для backend.
Контур Auth считается завершённым только при наличии:

корректного JWT;
успешного ответа /diag/whoami.

🧠 Принятые решения

Диспетчерская строится вокруг текущей ситуации

Основной вопрос диспетчера:

«Что происходит сейчас?»

а не:

«Что происходило раньше?»

Поэтому развитие диспетчерской начинается со статусов и оперативного управления, а не с отчётности и календарных представлений.

Архив и отчётность отложены

При анализе ADR‑004 и ADR‑007 подтверждено:

Audit + Sessions = единственный источник истины.

Следовательно:

- Архив
- Отчёты
- Метрики
- SLA

должны строиться через события и рабочие сессии, а не через список тикетов на frontend.

Выявлен отсутствующий доменный объект

В процессе проектирования диспетчерской обнаружено отсутствие модели Priority.

При этом ADR‑007 уже предполагает существование приоритетов через SLA‑политику.

Зафиксирована необходимость введения Priority как отдельной независимой оси системы.

📌 Следующий архитектурный шаг

Подготовить новый документ:

ADR‑008 — Ticket Priority Model

Предварительная модель:

EMERGENCY
NORMAL
PLANNED

Инвариант:

Priority не влияет на Status.
Status не влияет на Priority.
